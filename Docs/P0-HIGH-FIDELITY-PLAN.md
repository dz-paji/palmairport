# 机场协作：完整 P0 高保真原型实施计划

日期：2026-09-21；当前执行状态更新于 2026-10-04：M0–M4、M6 已实现并有本机验证，进入 M7 联调与交付。用户确认本轮先完成开发和本机验收，真机暂缺，不部署云端；当前执行计划见 [M7](M7-DELIVERY-PLAN.md)。下文早期建议若与后续已批准模块记录冲突，以后续定稿为准。

需求依据：根目录 `02-PRD.html` 的需求正文及内嵌原型图。原定交付目标为 Unity 完整 P0。**2026-10-04 用户确认本轮跳过 M5，语音与交流管理延期；本轮按调整后的 P0 范围交付，包含真实局域网联机与账号。**首轮以 **两台 Android 真机验收，并保留 Mac 开发入口**。

## 1. 交付目标与范围

交付一个可安装、可真实双人游玩的横屏移动端原型，完成：

**机舱大厅 → 游客 + bot / 双方登录后局域网组队 → 5 分钟机场班岗 → 星级与自动回放 → 分享 / 重试 / 返回大厅。**

- 场景、美术、HUD、动态反馈与 PRD 的热带海岛机场方向一致；场景为真实可交互的 3D 空间。
- 四类任务、共享车辆、旅客阻车、航班叠压、送错后果、bot 及异常状态实际运行。
- 登录、年龄准入、局域网发现及入房、结算同步、视频导出与系统分享使用真实实现。开发过程可以使用测试替身，但模块最终验收不能以演示状态代替真实功能。
- 先完成一张可反复游玩的机场关卡。下一关入口保留明确的未开放反馈；额外关卡作为后续内容单独评审。
- 本轮跳过 M5（F21）：实时语音、静音/屏蔽、麦克风权限与恢复、举报后台流程延期，不计入本轮验收；保留后续需求，不标记为已完成。
- MVP 不包含：公网游戏联机、房间码、深链自动入房、金币、装修、跨局关系记录 A/B、转机行李、清洁任务、投掷和航站楼跨区协作。
- “非玩家能上手”“两人明显更高效”“愿意再来一局”等目标通过真人 playtest 验证，不用程序检查代替。

## 3. 高保真标准

以 PRD 的局内 v7、机舱大厅 v11、结算 v2 为视觉参照，文字规则优先于示意图。

- **构图**：左侧餐食站、登机口、行李站、燃油站；中央道路与人行横道；右侧停机坪；海岸作为外围环境。场景装饰不遮挡交互点和路径。
- **镜头**：建议局内使用有明显纵深的斜视镜头，结算切换全机场顶部俯视。PRD 对“俯视”的表述与局内配图存在理解空间，M1 以实际画面确认角度。
- **美术**：明亮、圆润的玩具感 3D；飞机、三类车辆、货物和角色具备明确轮廓；区分物体表面材质，使用柔和阴影、海水与沙滩层次。首先打磨一个机位、一辆车和一个站点作为品质样板。
- **颜色**：餐食橙色、行李蓝色、燃油绿色、登机青蓝色；玩家身份使用独立标记。状态同时使用图标、文字或形状，避免仅靠红绿判断。
- **HUD**：左上班岗时间、顶部航班表、右上语音及设置、左下摇杆、右下情境动作。进度和错误尽量在对象附近呈现；手机尺寸下不出现长篇常驻教学。
- **状态覆盖**：默认、接近高亮、可交互、按住进行、被占用、等待、完成、失败、断线、禁用、恢复。按钮文案随当前动作变化。
- **动画与声音**：角色行走/驾驶、装卸、软管连接、旅客排队、飞机进出场、任务完成与倒计时提示。声音、图标和动作共同表达反馈。
- **适配**：以 16:9 横屏定构图，同时检查长屏、安全区与触控热区。性能目标先按选定真机实测确定，不以编辑器帧率代替。

M3 拆分如下，每次只推进一个可验收的玩法模块：

1. **M3.1 餐食 + 共享车辆**：下单 → 等待 → 出货口阻塞 → 装车 → 运送 → 卸货 → 空车复用。同时建立对象占用、装载归属、交付进度和取消的公共规则。
2. **M3.2 行李**：到达行李卸下并运回 → 出发行李选航班装车 → 对接交付；送错后立即展示失败，记录供回放使用。
3. **M3.3 燃油**：站内储备（大资源库）→ 加油站式油枪加注油车（徒步拿枪 → 插到油车 → 站内开阀，在油车上不可操作）→ 驾驶 → 机位接管/加注 → 收管；单人可完成，两人接力有可测量收益。2026-10-05 M3.3r 简化：全部单次点按；关阀后站内油枪自动归位、永不随车；机位改用油车自带车载油管，点飞机接管自动加注、再点断开自动收回；满箱 / 满机仍开阀或接管 2 秒宽限后漫油（见 [M3-TASKS-PLAN.md](M3-TASKS-PLAN.md) M3.3r）。漫油事件随本模块一并交付（2026-10-01 定稿纳入，触发与处罚在 M3.3 设计定稿）。
4. **M3.4 登机**：选择航班 → 可见队伍与路线 → 玩家放行 → 旅客穿越道路阻挡车辆 → 登机完成。若支持关闭登机口，仅停止新旅客放行，已出发旅客继续，避免队伍被任意撤销。

本轮顺序：M0 → M1 → M2 → M3 → M4 → M6 → M7；M5 跳过并延期，不阻塞 M6。M4 尚未完成的真人与真机验收继续保留，不因跳过 M5 自动通过。账号调研、资源盘点可在前期并行开展；所有影响玩法的联机状态约定在 M3 前完成。

## 5. 技术边界与完整 P0 的要求

- **状态与表现分离**：提取任务、航班、车辆、占用、旅客及评分状态；场景显示订阅状态。两套现有控制器不继续各自增加产品功能。
- **稳定对象标识**：账号、参局身份、玩家、车辆、任务、航班均使用稳定 ID，网络与回放不保存 Unity 对象引用或可继续变化的状态引用。
- **联机**：采用单一权威端裁定任务、占用、航班与结算，客户端提交操作意图；表现层处理移动平滑。先验证同时抢车、重复消息、乱序、断线和恢复，再扩展任务。
- **房主退出**：PRD 未给实现方案。建议持续复制足够的对局快照，剩余设备接任权威端并给退出席位配置 bot。M2 做技术验证，M4 做完整班岗验收；迁移后的结算使用新的有效权限，不能依赖退出者凭据。
- **账号与记录**：游客可完整 solo + bot；真人组队必须真实认证。掉线登出及再次认证、参与结算资格、年龄准入及拦截记录均按明确规则实现。游客成绩是否登录后迁移、具体准入规则另行定稿。
- **bot**：使用与真人相同的操作接口和占用限制；不能绕过资源竞争。加入本地可持久化的协作偏好/历史数据以承接“存留记忆”，具体记忆内容在 M0 明确。
- **真实服务范围**：局域网限定游戏通信，不等同于账号、语音、分享可离线运行。断网时游客 + bot 仍应可玩；真人流程在外部服务不可用时提供清晰反馈。
- **语音和举报（本轮延期）**：随 M5 跳过，不计入本轮 P0 验收。后续恢复时，语音服务与游戏传输解耦；举报需真实存储、处理入口及处理时限，并明确运营规则。
- **分享**：邀请链接用于下载/打开及说明岗位，不承诺深链进房；结算输出可分享视频，默认排除另一位玩家语音。分别验证实际平台分享入口和用户取消/目标应用未安装状态，不把打开分享面板记作发布成功。
- **回放**：记录不可变快照和关键事件，覆盖飞机、旅客、载货、任务失败及堵车；结束停帧。MVP 不显示拖动、暂停、倍速控件。
- **埋点**：记录邀请链接进入、登录、发现房间、入房、开局、首局完成、重试和分享结果；事件带对局与参与者标识并去重，支持观察邀请到双人首局的转化及 solo 玩家后续是否邀请真人。留存目标是验证指标，不是本轮可直接保证的结果。
- **运行检查**：业务状态测试 + 双端集成测试 + 真机权限/网络测试 + 人工视觉与体验验收。纯逻辑测试通过不能代替完整体验验收。

## 7. 整体完成标准

- 所有 P0 功能都有实现位置、验证步骤和证据，未实现服务不得标为已完成。
- 两台目标真机从首次安装到登录、同网入房、五分钟班岗、结算再开局完整可重复；游客 + bot 不被登录阻断。
- 实际测量进房步骤；登录和首次准入也计入 PRD 的低摩擦评估，不能只测已登录用户。
- 断开任一设备，包括房主，剩余设备能继续当局；退出账号不获得 bot 代打和结算进度；返回大厅后可再次登录组队。
- 任务进度、物资、占用、时间、评分在双端一致；归零不接受移动和交互；已完成任务保留。
- 信息板在手机上清晰，屏外搭档有标识，无语音情况下也可完成任务；真实语音及管理功能随 M5 延期，不计入本轮验收。
- 回放来自实际对局，结束停帧；视频可导出分享；分享、重试、下一关、大厅四入口均按约定处理。
- 真人 playtest 记录上手时间、完成架数、车辆分工、燃油接力、堵车归因及重试意愿；区分观察事实与体验假设。
